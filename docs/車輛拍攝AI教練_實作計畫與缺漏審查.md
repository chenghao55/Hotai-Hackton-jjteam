## 4. 架構與資料流

建議 Python + FastAPI + Ultralytics + OpenCV + Pydantic，版本在模型載入與相依測試成功後固定。啟動時載入模型並暖機，每張照片共用已初始化的推論服務；先做單一服務原型，量測後才增加推論工作者或匯出 ONNX。

即時路徑：

C 相機預覽 → D 的授權入口或代理 → A 輸入驗證與方向校正 → 品質量測及 YOLO → 目標關聯 → 六視角規則 → 漏斗裁決 → 時序穩定 → 回傳 C 顯示一條主要建議。

計算與提示順序分開：先做低成本全圖光線／模糊量測，必要時提前拒絕；YOLO 成功後再於車身或內裝 ROI 重算局部品質。使用者看到的主因依更新後 L1 到 L5 順序。不能讓背景明亮掩蓋車身過暗，也不能因 YOLO 未找到車身就跳過品質處理。

正式照片路徑：

拍下高解析度照片 → 重新檢查實際上傳照片 → 通過後由 D 保存並更新該槽位 → 六槽完成 → 借還配對／比較。預覽 PASS 不能直接當成正式照片已合格；照片被重拍替換時，舊的合格結果必須失效。

## 5. 漏斗演算法

### 5.1 共通規則

每層回傳 pass、fail、unknown、not_applicable 或 not_evaluated；被提前截斷而未執行的層是 not_evaluated，不能寫 pass。每層保存量測值、判定依據、門檻版本及原因代碼。

所有第一版必要檢查都已評估且通過才能自動 PASS。未知結果不得假裝通過；第一版必要條件改為品質、主體、占比、置中、指定槽位的特徵與幾何模板符合度。精確高度與角度估測移出第一版验收，不能因未計算真實高度而阻擋已符合模板的照片。

同層的暗、逆光、反光在真實畫面可能並存。保留多個診斷旗標，但採固定且可測試的裁決順序，只顯示一條 primary_issue。同樣地，過近與截斷也要保存不同原因，避免把所有缺角都解釋成距離問題。

### 5.2 層級設計

| 層級 | 指標／方法 | 決策與限制 |
|---|---|---|
| 輸入前置 | 解碼、檔案大小、像素上限、EXIF、鏡像、影格識別 | 無法解碼直接回傳明確 API 錯誤，不進模型 |
| L1 光線 | 亮度分位數、暗／亮像素比例；有 ROI 後重算主體曝光與局部飽和 | 區分全圖過暗、主體暗背景亮、主體大面積反光；白色車身不等於過曝 |
| L2 清晰度 | 固定分析尺度的 Laplacian／Tenengrad，兼看主體 ROI | 門檻依縮圖、壓縮、噪聲與場景校正；單張模糊不能確定是手震還是失焦 |
| 主體可判定性 | 車身或座艙特徵的置信度、數量、位置與關聯 | 沒車、多車不明或嚴重遮擋時回傳 unknown／明確重拍，不算距離與角度合格 |
| L3 距離／完整度 | 主體寬高占比、面積占比、四邊餘裕、觸邊及完整度證據 | 回傳太遠、過近或被截斷；bbox 未觸邊也不保證車身完整；不推算公尺或固定步數 |
| L4 置中 | 主體中心相對視角模板的水平／垂直偏移 | 採正規化座標，前後排使用各自模板；避免把主體偏低當成相機太低 |
| L5 相對幾何與槽位模板符合度 | 指定特徵可見性、相對位置、帶方向的框間距與尺寸比例，對照各槽位基準及容許範圍 | 原高度與角度合併；回傳模板符合／偏離／無法確認，不由偏差直接斷言相機高度或唯一移動方向。內裝採獨立模板 |
| PASS | 所有必要條件成立且短時穩定 | 允許拍照；正式照片仍重新檢查 |

正規化幾何的例子：車身寬度占比=(x2-x1)/W，中心偏移=((x1+x2)/2-W/2)/W。這是構圖比例，不是相機距離估測。

多車情境先以取景框重疊、中心接近程度、面積及置信度選擇候選，再把燈、牌、輪子依位置關聯到同一輛車。若無法確定目標，要求只保留目標車輛；不能拿鄰車的輪子或車牌補足條件。

門檻集中在版本化設定檔，按 exterior／interior／shot_type 分開。先用標註校正集定值，不提供看似精準但未驗證的固定亮度、模糊或比例門檻。

### 5.3 指導語與時序

- TOO_DARK：光線不足，請開啟補光或移到較明亮的位置。是否顯示「照明按鈕」依 C 回傳的裝置能力決定。
- BACKLIT：車身較暗、背景過亮，請微調站位或曝光。
- BLUR：畫面模糊，請拿穩手機並重新對焦。
- TOO_FAR：請稍微靠近，讓車身接近取景框。
- BODY_CROPPED：車身未完整入鏡，請調整距離與鏡頭，保留車頭、車尾和輪胎。
- OFF_CENTER：請微調手機方向，讓車身對齊取景框。
- FRONT_VIEW_INCOMPLETE：請依前排示意圖，讓方向盤與前排座位一起入鏡。
- REAR_SEAT_INCOMPLETE：請將鏡頭對準整排後座，保留椅背與坐墊。
- GEOMETRY_UNCERTAIN：目前無法確認構圖，請依示意圖調整；持續無法確認可轉人工協助。
- READY：構圖、特徵與畫質符合要求，請保持穩定並拍照。

前後左右移動文案必須依目前槽位及足夠的方向證據決定；沒有車身方向證據就使用示意圖提示，不能猜「往左走」。後方照片不得要求大燈入鏡。

起始實驗設定：預覽每秒送 2 張左右、每個工作階段最多一張待推論，保留最新影格；合格持續約 0.8–1 秒才顯示 READY，提示文字設最短停留時間與遲滯。以上均需依實測調整。舊回應依 session_id、shot_type、frame_id 丟棄；高優先品質失敗或回應過期時立即取消 READY。

提供受控的人工處理出口。網路或模型長時間不可用時顯示原因並交給 D／C 的既定流程，不能永久鎖住使用者，也不能偷偷當作通過。

## 6. API 契約草案

以下為第一版已實作的局部契約草案，不宣稱 PDF 已定義；正式跨組契約仍需由 A／C／D／E 凍結。實際欄位以 `docs/照片API契約.md` 和程式為準。

### 6.1 即時照片輸入

POST /api/v1/capture/analyze
Content-Type: multipart/form-data

- image：JPEG 或 PNG 二進位。初版可採單檔上限 10 MB、解碼上限 20 MP，最終值須與 C 的正式照片規格一致。HEIC 支援需明確決定；未支援時回傳 415。
- metadata：JSON 字串，使用同一個版本化 schema。

範例：

~~~json
{
  "schema_version": "1.0",
  "case_id": "CASE-001",
  "capture_session_id": "SESSION-001",
  "capture_phase": "checkout",
  "shot_type": "exterior_front_left",
  "frame_id": 42,
  "mode": "preview",
  "image_mirrored": false,
  "client_capabilities": {"torch": true}
}
~~~

capture_phase 為 checkout／return；mode 為 preview／final。case_id 由 D 建立並驗證存取權；工作階段、槽位與正式照片 ID 不得混用。尺寸由解碼後影像取得，EXIF 先校正再做推論，必要時回傳校正後尺寸。原始方向到 UI 顯示的映射由 C／A 一起測試。

### 6.3 與 PDF 統一 schema 的銜接

| 欄位 | 負責者 | 處理方式 |
|---|---|---|
| case_id | D | A 原樣回傳已授權案件 ID |
| capture_quality | A | 本階段實作 |
| vehicle_change | A 的比較階段 | 未比較標記 not_run，不能填 aligned=true 或無變化 |
| damage_type、cleanliness | B | 尚未執行時不得填 clean 或任意車損類別 |
| risk_level | D | 不能由 A 的清晰度任意推成低風險 |
| confidence | 各模組＋D 契約 | 定義所指對象；保留品質、對位、差異、B 的獨立信心 |
| recommended_action | A／B 建議，D 決定案件行動 | A 只建議 pass／reshoot／human_review；清潔／維修由後續決策 |

建議 D 對外提供完整聚合結果，A 提供上述局部結果，保持欄位名稱一致。若要求 A 也輸出整份 envelope，必須先把未執行欄位的 nullable／status 規則寫入 schema 並升版。原 PDF 的 cleanliness 與 risk_level 列舉没有未執行狀態，不能未經契約協調就塞入 null／unknown。

特別區分：「capture pass」只代表照片可用，不代表沒有車損、案件通過或能自動完成還車。

### 6.4 錯誤、正式照片與儲存

- 合法照片的品質不合格：200，明確 reshoot；不要用 500。
- 413 過大、415 不支援格式、422 無法解碼／欄位不合法、429 過載、503 模型未就緒；逾時由入口與服務約定一致的錯誤代碼。
- 錯誤回傳 request_id、code、可操作 message、retryable，沒有模型結果時不捏造品質分數。
- health 檢查程序存活，readiness 檢查模型已載入且暖機成功；模型缺失時服務不得假裝 ready。
- final 請求以照片雜湊／請求 ID 實作冪等；D 保存原始證據、slot 狀態與分析版本。重試不重複新增證據。
- 預覽影格預設不長期保存；除錯抽樣另行約定。原圖、車牌與人臉受存取控制；對 E 的公開 Demo 證據去識別，不公開原始圖片 URL。
- 初版採 binary upload，若未來增加 URL 輸入，再另定允許來源、逾時及下載限制。

## 7. 模型與資料工作

### 7.1 必須先做的稽核

1. 核對 data.yaml、class_id 對照與各類別圖片／框數；class 1 已停用，未來重訓時才整理標註與重新編碼。
2. 查 headlight 是否包含尾燈；若命名與標註不一致，先清理定義，再決定保留、拆類或重訓。
3. 取得原訓練設定、results.csv、逐類 PR／confusion matrix、資料切分方式及各類樣本。
4. 載入 best.pt，檢查 model.names，跑固定六視角／失敗樣本，測量 CPU／GPU 延遲與各類別漏檢。
5. 車輛、場景與拍攝序列分組切分資料，避免相邻影格或同車同場景同時出現在訓練與測試集；門檻只用校正集調整，保留獨立測試集。

### 7.2 既有資料與模板優先的路線

使用者會提供左前／右前／左後／右後各自的 bounding box 基準點。第一版以 API 指定 shot_type 的模板符合性檢查為主；四模板自動分類另輸出最佳匹配槽位與歧義狀態，不能把選定槽位當成模型已辨識正確。

輸入資料：原始照片、data.yaml、YOLO 標註、每張 shot_type、構圖可接受／不可接受及原因（若有）、既有車輛／場景分組。現有偵測標註通常沒有視角與品質標籤，可先對既有照片補標，不必重新拍攝。

各模板提供畫布寬高、橫直向／鏡像規則、車身和必要物件的框或中心＋尺寸、必要／選用物件、可見數量與容許誤差。只有點可做位置匹配，完整框才支援尺寸比例。多輪／多燈使用同類物件集合匹配；不能僅以畫面左右排序就命名為前輪／後輪。

先完成 L3 占比與 L4 置中，再於同一目標車身座標系計算物件中心位置、帶方向的水平／垂直間距及尺寸比例。例：dx=(cx_i-cx_j)/car_width，dy=(cy_i-cy_j)/car_height。UI 基準點先轉到原圖座標；各內裝模板採定義好的獨立參考區域。

L5 以各特徵相對模板中心值的偏差除以容許誤差，加權彙整為 template_error；這是誤差分數，不是正確率。必要特徵缺失先標記無法確認／需重拍，不得只比較剩餘少數框就給低誤差。四模板分類要求最佳誤差足夠小，且與第二名差距足夠大，否則回傳 ambiguous／unknown；方向與相機高度的精確數字不輸出。

可先每槽抽 20–30 張不同車輛／場景的既有照片供資料稽核，並加入錯構圖及跨槽照片；這是起始抽樣，不是足以證明準確度的門檻。按車輛／場景／序列分組保留未用於定模板或調門檻的評估資料。若全部照片已參與 YOLO 訓練，只能報既有資料上的診斷結果，不宣稱獨立泛化評估。

沒有新實拍仍可評估模板匹配，但不能聲稱已驗證現場提示效果、手機延遲與連續操作體驗。影像裁切／亮暗／模糊擾動可補規則測試；不能拿水平翻轉或二維拉伸當成真實另一車角或高度的證據。

先測幾何是否能區分模板；若前後模板相似或欠缺尾燈等證據，明確拒判。只有現有資料證明有需要才考慮新增視角模型或關鍵點，不列為第一版必要前置。

### 7.3 車牌文字辨識候選（使用者已決定延後）

此段保留作未來參考，本次不安裝、不實作、不接外部服務。使用者完成拍攝教練後再決定是否採用 PaddleOCR PP-OCRv5 文字辨識模組：既有 YOLO license_plate 框 → 原始解析度裁切及必要的文字區域定位／校正 → OCR → 格式正規化 → 與 D 提供的預期車牌比對。嚴重斜角要取得車牌四角或文字四邊形才能做有依據的透視校正，軸對齊 bbox 本身不提供這些角點。

官方文字辨識模組：https://paddlepaddle.github.io/PaddleOCR/main/en/version3.x/module_usage/text_recognition.html 。另可評估專用 Plate Recognizer，其官方支援名單列有 Taiwan：https://platerecognizer.com/countries 。需以使用者照片比較整牌完全正確率、拒判率與延遲，不能引用通用 OCR 分數宣稱臺灣車牌表現。

OCR 輸出文字、信心與 match／mismatch／unknown；模糊、過小、反光時回 unknown，不把低信心錯讀直接視為錯車。OCR 相符可提供車牌一致性證據，不等於完整車輛身分認證。此功能目前為候選方案，尚未安裝、連線外部服務或實作。

## 8. A 尚需完成的借還比對

此路徑與即時教練分離，採非同步工作，避免拖慢預覽回應。

1. D 按同一租借案件、車輛、checkout／return、shot_type 配對；缺少基準照片、錯槽位或品質不合格就明確中止或送人工。
2. 在車身／內裝有效 ROI 做對位，排除背景；先建立特徵匹配與 RANSAC 的基準，並輸出匹配數、內點比例、重投影誤差及重疊覆蓋度。
3. 車輛是三維且表面反光，單一 homography 對大角度差不可靠；限制近似同視角，必要時做局部／分區對位，不能宣稱任意借還照片都能可靠比較。
4. 對位品質不足回傳 aligned=false、明確 reason 及 human_review，後續差異不判定為無異常。
5. 在有效重疊區計算差異圖，抑制光照與背景影響，輸出差異遮罩、熱區框／裁切與差異信心。SSIM 或像素差只能作基準，不直接等於車損。
6. 與 B 約定遮罩／框／裁切格式、參考原圖、大小、座標系及變換矩陣；與 D 約定 artifact_id 及受控取得方式。

比較輸出需能表達 aligned=true 但 change_detected=unknown，以及 aligned=false 而無法比較。圖像差異不能替代 B 的損傷語意，更不能替代理賠定責。

## 9. 驗證與验收

以下數字是建議驗收目標，不是實測成績。第一週由 A／C／D／E 依硬體與資料量確認。

| 面向 | 方法 | 建議通過標準 |
|---|---|---|
| 介面 | 合法／缺欄／錯格式／過大／亂序／重試契約案例 | 約定案例全部通過，錯誤都有可操作回應 |
| 漏斗 | 單缺陷與多缺陷組合、unknown、未執行層 | L1–L5 優先順序符合標註；必要 unknown 不可自動 PASS |
| 品質攔截 | 各視角的人工標註獨立測試集 | 明顯不可用照片攔截召回率目標 ≥95%，可用照片誤拒率目標 ≤10% |
| 六槽辨識 | 各槽 confusion matrix、左右／前後混淆、拒判比例 | 每槽 precision／recall 與自動判定覆蓋率分開報告，不以平均數掩蓋弱項；第一週設定可達門檻 |
| 使用體驗 | 可取得的既有序列及模擬亂序／抖動；無實拍序列時標記尚未現場驗證 | 提示不反覆跳動，失效照片不沿用 READY，後排不顯示方向盤要求 |
| 延遲 | 指定硬體、圖片規格、暖機狀態、併發數 | 先以單使用者端到端 p95 ≤800 ms 為原型目標；伺服器耗時與網路耗時分開報告 |
| 案件狀態 | 六張正式照片、替換、缺槽、未知與人工路徑 | 只有六槽有效合格才可自動完成；人工接受須留獨立紀錄 |
| 借還比對 | 無變化／真變化／僅光線變化／錯視角／遮擋 | 報告差異召回、誤報與對位拒判；對位失敗不判無變化 |

起步資料建議每視角至少 30 張合格與 30 張不合格作 smoke／校正起點，另保留按車輛／場景獨立的測試集及連續拍攝短序列。這是啟動規模，不能支持商用泛化宣稱。報告提供每組樣本數、分母與信賴區間，資料不足就明示。

全案六情境端到端測試建議為：正常、須重拍、疑似外觀異常、需清潔、無法判斷需人工、系統／網路失敗與恢復。這是供 E 確認的提案；總覽没有列出六情境內容，也不能把六情境直接解釋成六個拍攝角度。
