# 借還車照片對位與差異熱區計畫書（沿用正式上傳流程）

日期：2026-09-28　｜　範圍：借車前與還車後照片的可比較性、對位、差異熱區、重拍原因及跨組交接

## 1. 目標與完成定義

用同一輛車、同一拍攝視角的借車照片與還車照片，找出「值得檢查的可見變化區域」，並提供兩張原圖、對位結果、熱區位置與無法比較的原因。熱區是影像差異候選，不宣稱車損種類、責任或是否索賠；車況語意由 B 判斷，案件與人工審理規則由 D 決定。

第一版完成條件：至少一個車外視角能在**保留測試資料**上重現完整流程；對位失敗會回明確狀態與有證據的重拍提示；對位成功但局部不可見時只標示可比較區域；熱區可回溯借／還照片 ID 與演算法版本。其餘視角按資料逐步開放，不能以一個視角的結果宣稱六視角都有效。

## 2. 已有能力、缺口與本計畫假設

目前主專案由 E 提供 `POST /photo-guidance`（預覽、不保存）及 `POST /photos`（正式照片重新檢查，合格才由 A 保存並取得 `photo_id`）。A 的 `PhotoCoach` 已接入 E，但模板仍未用真實照片校正，因此真實自動 PASS 尚未開放；「允許拍攝但需人工審理」目前也**不能**由正式上傳流程保存成待審照片。`POST /cases/from-photos` 在照片收集完後才由 E 建立 `case_id`；現行前端主要走還車照片流程，不能假設它已能取得同一租借的借車照片。B 已支援成對照片作為證據，但目前的車況模型是逐張分析，尚未做真正的前後影像比對。

使用者已決定沿用既有正式上傳流程：先經教練檢查、由 A 保存，取得 `photo_id` 後再做借還對位。先前「候選照暫存、先對位再正式保存」的方案不採用。串接仍需解決兩件事：

1. 從可信來源取得同一租借／車輛的借車基準照片，而不是靠使用者自行指定任意借車照。現行 E 的 `case_id` 在收齊照片後才產生，不適合作為拍攝前的配對鍵。暫稱 `rental_id`，正式名稱由 E／D 定案。
2. 現有 `/photos` 只有教練 PASS 才保存；模板尚未經真實照片校正，真實自動 PASS 仍未開放。要讓現場借／還照片進入比較，需先完成模板校正與正式上傳流程，或由團隊另行確定待審證據保存契約。比較模組不繞過這項限制。

既有雲端資料分成「有進行索賠」與「沒進行索賠」，各包含一組組借／還照片。本機已有對應原圖，可在不加入 Git 的前提下做離線抽查。依檔名暫配得到未索賠 120 對、索賠 21 對；這只是候選數，尚未人工核對同車、同視角、重拍版本與標註。抽看發現：未索賠組的借／還照片可呈現近似車角；索賠組中有借車全車角對應還車局部車頭特寫，也有「還2」及單獨車況回報照。因此檔名相近仍須人工核對可比較性，局部特寫應先走視角／覆蓋不足的拒判，不拿來評估熱區召回。索賠分類是**案件層級標籤**，不能當作某張照片／某個熱區的影像真值。

### 2.1 核對 `module_a/photo.py` 與 `module_a/__init__.py` 後的儲存事實

`module_a/__init__.py` 已公開 `PhotoType`、`CaptureSlot`、`Photo`、`PhotoNotFoundError`、`save_photo`、`get_photo`、`get_photo_info`，比較流程應優先透過這些既有介面或 E 的 `PhotoStorageService` 存取，不直接讀寫 `PHOTOS_DIR`。`PhotoType` 為 `borrow`／`return`；`CaptureSlot` 除四角及前後排，也包含 `rear`、`fuel_parking_card`、`other_damage`，其中 `other_damage` 只可用於還車。

`save_photo(file_bytes, photo_type, capture_slot, mime_type)` 產生唯一 `photo_id`，在本機保存**傳入的原始 bytes**及四個中繼欄位；`get_photo(photo_id)` 取回原始 bytes，`get_photo_info(photo_id)` 取回 `Photo` 中繼資料（含本機 `file_path`）。儲存函式本身只驗證型別、槽位組合與非空 MIME 字串；影像是否可解碼、品質是否合格由上游流程處理。找不到或中繼資料損壞時會拋 `PhotoNotFoundError`。

目前 `Photo` **沒有**租借／車輛 ID、拍攝時間、車型、`entry_side`、品質結果、影像雜湊或照片版本，也沒有列出某租借所有照片、配對、替換或刪除的公開介面。因此不能只憑兩張 `Photo` 自動證明同車同案件，不能把檔案路徑當跨服務 ID。這些關聯及狀態須由 E／案件來源的受控索引提供；若需要改 A 的公開資料模型，先確認最小相容擴充及其使用者。

## 3. 責任與交接

下表是待確認的**提案**。根目錄 `README.md` 目前定義 A 為照片儲存與拍攝教練、B 為車況 AI、D 為案件與審理、E 為 HTTP／整合、UI 為前端；C 尚未有穩定的公開責任。使用者已表示「顯示借車參考圖」應由 C 實作，這需與團隊現有 UI 分工確認，在確認前不得把它寫成現況。

| 工作 | 提案負責 | 交付界線 |
|---|---|---|
| 借／還原圖保存、照片 ID／現有中繼資料；教練解碼時處理 EXIF | A | `save_photo` 保存原始 bytes；不建立案件、不判車損 |
| 單張照片的曝光、清晰度與構圖診斷 | A 的既有教練 | 可供重拍原因參考；單張診斷不能解釋全部配對失敗 |
| 影像對位、可比較區、熱區候選產生 | A 的比較核心原型 | 熱區不直接判車損；跨組交接仍需定案 |
| 車損／整潔等語意判讀，以及接到既有車況發現 | B | 保留兩張照片與熱區的證據來源，不決定案件規則 |
| 基準照片與租借關聯、案件／人工審理決策 | D 的規則，E 的資料接線 | 不以重拍次數或熱區自行定責 |
| 正式照片上傳、受控取圖、未來比較 API 與跨模組協調 | E | 對外 schema 與路由由 E 擁有；沿用現有 `/photos` |
| 借車參考圖、重拍原因及使用者操作 | C／UI 待團隊定案 | 依 A／比較模組的原因碼呈現；前端不推測失敗原因 |

交接會議需確認：C 是否就是相機／使用者端、誰負責借車參考圖、可信 `rental_id` 與基準照片從哪裡取得、A 的熱區候選如何交給 B。A 先做不改動 E／B／D 契約的比較原型；跨組串接前再凍結公開契約。

## 4. 使用者流程：正式照片先通過，再比較

```text
C／UI 拍下正式還車照片
  → E 的 /photos 讓 A 教練重新檢查正式照片
      ├─ 不合格 → C／UI 顯示教練原因，使用者重拍；不產生 photo_id
      └─ 合格 → A 保存原圖，E 回傳 photo_id
                   → E 從可信租借關聯取得同視角借車 photo_id
                   → A 比較核心取回兩張照片，對位並評估可比較性
                       ├─ 可比較 → 產生熱區候選，後續交 B 判讀
                       └─ 不可比較 → 回傳有證據的失敗原因
                                        → C／UI 顯示參考圖及重拍指引
                                        → 仍失敗時交人工處理
```

目前 `PhotoCoach.analyze(image, context)` 只接收**一張照片**與拍攝視角等資訊，拿它與固定構圖模板比較；輸入沒有借車照片 ID 或借車影像。因此「教練通過」只保證單張照片符合已校正的拍攝規則，**不能保證與那次借車的照片對位成功**。例如兩張照片各自都清楚、完整，但借車偏正面、還車偏側面，車身同一區域仍可能無法重疊。對位成功也不等於細小刮痕可辨識；只有有效區域的畫質足夠，才交付熱區候選。已通過教練的還車照若對位失敗，可保留原本 `photo_id` 作為紀錄；租借關聯須指向最後採用的照片 ID，不把舊照誤當現行照片。

若產品要求「教練一通過就保證可與借車照比較」，需把**同一租借的借車基準照片**納入預覽與正式照片的判定，將兩張照片的重疊／對位品質也設為通過條件，並修改 A／E／C 的輸入與回應契約、用真實配對資料校正。這是可考慮的下一版整合，不是目前教練已具備的能力；即使加入，遇到基準缺失或嚴重遮擋仍要有無法判定出口。

借車基準在借車階段已保存與驗證，還車時讀取既有照片與記錄，不重跑一次完整拍攝教練。仍須評估這一對照片的實際重疊與可比較性。當借車基準缺失、損毀或客觀上無法比較，重拍還車照未必能解決，應回系統／人工處理原因，不把責任錯誤推給使用者。

重拍採**有原因、有上限**的政策：首次不可比較時給一次明確修正指引；再失敗時可換一種有根據的提示，或依團隊設定的次數／時間上限走人工。上限值要用實拍試驗與 UI 流程確認，不在資料不足時寫死。人工出口由 D 的流程定義；A／比較模組只回技術結果。

## 5. 配對與輸入資料契約草案

既有正式照片仍沿用 JPEG／PNG 原圖與 A 的 `PhotoType`／`CaptureSlot`；比較介面建議**傳兩個已保存的照片 ID**，由 E／A 的既有讀取介面取回原圖，避免 C 向多個模組重傳圖片。

每對照片至少需：可信租借識別、車輛識別或其受控關聯、借車 `photo_id`、正式還車 `photo_id`、兩張照片各自的 `photo_type`、`capture_slot`、內裝 `entry_side`（若適用）、照片版本與拍攝時間。照片 ID 必須由後端產生；同一對照片不得僅以檔名或列表順序配對。四個車外角為第一階段比較對象；`REAR`、油卡、`OTHER_DAMAGE` 等現有槽位先不假設可配對。內裝前／後排與左右開門需獨立驗證後再開放。

正式還車照片被重拍替換時，舊比較結果必須依照片 ID／版本失效；現有 A metadata 沒有「目前有效版本」，需由租借照片關聯索引記錄目前採用的 `photo_id`。同一照片組重試應得到同一工作結果，避免重複建立熱區或證據。比較工作可非同步執行，但使用者等待、逾時、取消與狀態查詢由 E／C／UI 一起定義。原始照片與裁切圖片由受控 ID 取得，不把雲端原始 URL 或 `Photo.file_path` 放進公開結果。

EXIF 方向校正指按照片中的方向資訊將像素轉正，讓顯示、模型與熱區共用一致座標；它不會修正拍攝角度。`get_photo()` 取得的是未改動的原始 bytes，比較模組讀取後需在記憶體中解碼／轉正；轉正圖是分析產物，不能誤當 A 已保存的原圖。需記錄轉正後尺寸、處理版本與原圖雜湊。**熱區座標以 EXIF 轉正後的還車照片為基準**，在回應中明示座標系與寬高。

## 6. 對位與差異方法：以真實配對驗證

第一版用 OpenCV 建立可重現基準，而不是預設單一透視變換能處理整台立體車輛：

1. 先從原圖確認同車／同視角，取得車身有效區；排除背景、車牌資訊與大片可移動遮擋。若只能得到粗車身框，要量測框內背景造成的誤報，必要時加入人工或自動車身遮罩。
2. 在車身可見區做局部特徵匹配，建立保守的幾何對位；記錄匹配數、內點比例、重投影誤差、匹配點空間分布、有效車身重疊率及局部殘差。門檻從校正集決定，不能用「算出矩陣」當成功。
3. 由於 45° 車角同時包含不同深度的車頭／側面，若整體對位只貼合其中一面，先縮小可比較區；資料證明需要時再測車頭／車側分區對位。每區各自回報覆蓋與品質。若視角差過大，拒判並建議參照借車圖調整。
4. 在有效重疊區做亮度／色彩正規化與差異基準（像素差、局部 SSIM 等），針對反光、陰影、輪胎位置、遮擋及邊界錯位測誤報；再生成候選遮罩、熱區框與兩張照片的同位置裁切。
5. 熱區分數表示影像差異強度／排序，尚未校正前不能稱為車損機率。無熱區只代表**可比較區域內未見超過門檻的變化**；其餘區域保持未知。

OpenCV 是影像工具；受限制的是單一 homography 對不同深度物體的幾何假設。此處的方法是否足夠，必須由現有真實借還配對的對位殘差和差異誤報決定。

### 6.1 目前比較原型的實作範圍

`module_a.compare_stored_photos(borrow_photo_id, return_photo_id, detector=...)` 已能取回 A 儲存的兩張原圖、檢查借／還類型及相同車外視角、做 EXIF 轉正、以單一車身偵測框限制 SIFT 特徵、用 RANSAC 估計對位、計算重疊與重投影量測，並輸出候選熱區框、透明 PNG 熱圖與實際比較區遮罩。匹配點若只集中在局部車身，會以 `ALIGNMENT_LOCALIZED` 拒判；差異計算也限於對位內點圍出的支撐區域，不把透視變換外推到整個車框。熱區框座標對應轉正後的還車原圖；熱圖和遮罩另附共同的分析尺寸。

這是**離線原型**：目前使用單一 homography 與未校正固定門檻；粗車身框可能含背景，`overlap_ratio` 只代表偵測框的幾何重疊，不代表有效車身覆蓋。尚未加入車身分割、分區對位、人工核實過的真實配對驗證或 B 的車損判讀。以現有照片按檔名暫配後抽查 10 對，9 對保守拒判，1 對未索賠照片通過對位。加入內點支撐區限制後，該組候選熱區從 56 個降為 3 個；仍需人工核實這 3 個是否真變化，不能用索賠標籤當熱區真值，也不能從這 10 對推算模型準確率。結果只可用來檢查方法與資料流，不可用於自動判定車損、使用者責任或強制重拍。呼叫端必須先從可信租借資料確認兩張照片同車同租借，因為 `photo.py` 沒有這項資訊。

## 7. 結果與重拍原因契約草案

比較狀態最少區分 `COMPARABLE`、`RESHOOT_RECOMMENDED`、`HUMAN_REVIEW_REQUIRED`、`PAIR_INVALID`、`PROCESSING_FAILED`。只有 `COMPARABLE` 才計算並對外交付熱區；熱區為空也要附有效覆蓋區。各狀態均回照片 ID、拍攝視角、對位品質量測、原因碼及演算法版本，避免以 `aligned=false` 誤寫成「沒有變化」。

| 原因碼草案 | 成立條件 | 給 C／UI 的建議文字方向 |
|---|---|---|
| `RETURN_BLURRY` | 還車照片清晰度不足 | 拿穩手機、重新對焦後重拍 |
| `RETURN_EXPOSURE_UNUSABLE` | 還車車身過暗／大面積過曝 | 調整光線或站位後重拍 |
| `VIEW_OVERLAP_LOW` | 借還車身有效重疊不足且還車構圖可調整 | 顯示借車參考圖，依參考位置調整後重拍 |
| `OCCLUSION_HIGH` | 還車車身大面積被遮住 | 移開遮擋或換到能看見車身的位置後重拍 |
| `REFLECTION_HIGH` | 反光區域妨礙比較且可藉站位改善 | 微調站位，避開強反光後重拍 |
| `ALIGNMENT_UNCERTAIN` | 特徵不足或局部誤差大，無法歸因到單一動作 | 說明目前無法可靠比對，參照借車圖重拍；重試仍失敗轉人工 |
| `BORROW_BASELINE_UNAVAILABLE` | 借車照片缺失／讀取失敗／本身不可比較 | 回系統或人工處理，不要求使用者重拍來修復借車照 |
| `PAIR_MISMATCH` | 車輛、租借或視角識別不符 | 先核對配對資料；證據顯示拍錯還車視角時才提示重拍 |

若同時存在多個原因，保留所有診斷，但只呈現一個主要、可操作的提示。對位模組可指出「重疊不足」；單張教練可指出「模糊」或「曝光」；兩者不可互相冒用原因。重拍提示由 C／UI 呈現，參考圖的存取與顯示權限需由 E 提供受控介面。

交給 B 的最小結果：`pair_id`、borrow／return `photo_id`、拍攝視角、有效重疊遮罩或其 artifact ID、每個熱區的 ID／框／遮罩與前後裁切 artifact ID、座標系、對位量測與版本。B 自行判斷熱區是否屬於車損，保留其原有單張分析與來源 `source_photo_id` 契約；接到 D 的證據映射不得假造借車 ID。

## 8. 雲端資料整理與標註

先在**不改動原始雲端資料**的前提下，建立每組照片的清單：雲端相對路徑／受控 ID、案件組 ID、索賠資料夾標籤、借或還、候選拍攝視角、拍攝時間、尺寸、格式、可否讀取及雜湊。接著人工抽查組內是否同車、同視角；名稱或現有分類不可直接當真值。照片若含車牌或人臉，公開示例需去識別。

標註分三層：① 配對是否正確；② 是否可比較及失敗原因；③ 真正可見的新增／消失變化區域。至少涵蓋無變化、確有變化、只有光線／反光、視角偏移、遮擋和模糊。索賠／未索賠兩類都取樣，但不要把「有索賠」直接標成「有新車損」。

按車輛及租借案件分組切開校正集與保留測試集，同車近似照片不得跨集。先做一個車外視角的人工審查樣本與失敗清單，再依資料分布決定規模；資料少時報絕對筆數與比例，避免虛構準確率。

## 9. 評估與驗收

離線報告至少包含：配對正確率、可比較判定的錯放行／錯拒判、成功對位的有效車身覆蓋率與局部對位誤差、真變化熱區召回、無變化照片的誤報數、僅光照變化的誤報、每組處理時間，以及重拍一次後成功率。按視角、車型、光線與索賠資料夾分開報樣本數；門檻由校正集調整，保留集只用於最終檢驗。

不預先捏造量化通過率。第一階段的發佈門檻由 A／B／C／D／E 使用可用資料與使用者體驗要求確認；未達標視角回人工或保持功能關閉。評估時務必展示「成功但有假熱區」、「對位失敗需重拍」和「基準問題不能靠重拍修復」三種錯例。
